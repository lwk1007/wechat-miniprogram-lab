# 07 照片定时清理（云函数）

练：**云函数 + 定时触发器**。把「照片 24 小时自动删除」这句承诺真正落地。

## 跑起来

### 现在就能跑（演示模式，零配置）

直接导入本目录，`config.js` 里 `envId` 留空即可。
清理逻辑在本地照样跑一遍：点「造一条 25 小时前的测试记录」→「先演练」看命中几条 →「执行删除」真删掉。

> 演示模式不是假成功：它是**真按同样的规则**算过期、真删本地记录，流程和云端完全一致，只是执行者从云函数换成了本地代码。
> 这样你能先看清「扫描 → 命中 → 删除」的骨架，再去读云函数会非常快。

### 上云（真正做项目时）

1. 真实 AppID 打开，填 `config.js` 的 `envId`
2. 云开发控制台建集合 `pets`（权限「仅创建者可读写」）
3. 右键 `cloudfunctions/cleanup-photos` → **上传并部署（云端安装依赖）**
4. 云函数详情 → 版本与配置 → **上传触发器**（`config.json` 里已配好每天 3:00）
5. 回小程序，点「造一条 25 小时前的测试记录」→ 点「先演练」→ 再点「执行删除」

## 10 分钟讲解

| 位置 | 看什么 |
|---|---|
| `cloudfunctions/cleanup-photos/index.js` 的 `dryRun` | 默认只统计不删。**上线前必须有演练这一步**，否则一条写错的 where 就能清空数据库 |
| `where({ createdAt: _.lt(cutoff) })` | `cutoff = now - 24h`，这就是「24 小时」的全部逻辑 |
| 删除顺序 | 先 `cloud.deleteFile` 再 `doc().remove()`。反过来会留下永远找不到、也删不掉的孤儿文件 |
| `BATCH = 100` | 云函数单次查询上限 100，所以用 while 循环分批清 |
| `config.json` | `"0 0 3 * * * *"` 是 **7 段**（秒 分 时 日 月 周 年），不是 Linux 的 5 段 |

## 权限的关键差别

云函数用 `wx-server-sdk`，拿到的是**管理员权限**：能删别人创建的记录、能删云存储文件。
这也是为什么「自动清理」必须放云函数 —— 小程序客户端没有这个权限。

## 自测

1. 演练模式下 `scanned` 应该有数、`deletedDocs` 必须是 0。
2. 执行删除后去云开发「存储」里确认文件真没了，不只是记录没了。
3. 触发器日志：云开发控制台 → 云函数 → 日志，看每天 3:00 有没有执行记录。

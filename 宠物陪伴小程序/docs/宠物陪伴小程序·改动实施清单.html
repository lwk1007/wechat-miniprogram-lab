二、本次已完成的改动明细

2.1　场景拓展 第 2 条 · P0

目标：背景从「纯白单屏」变成「有场景、会活动」的陪伴空间。

  • 5 套场景：草地、窗台、客厅、海边、星空。全部用纯 CSS 绘制，各带独立环境动效（云飘、帘影、浪线、星光等），不引入任何图片资源，包体零增长。
  • 宠物自主活动：在场景内横向随机走动（24%~76% 范围），带走路起伏与朝向镜像翻转；停下时随机换一句状态文案，不再一直静止。
  • 按时间自动选场景：05–09 窗台、09–17 草地、17–20 海边、其余时段星空；用户手动切换后记住选择，不再被时间覆盖。
  • 修掉的隐患：切换场景时旧计时器未清，两套漫游同时运行导致宠物越走越快（见 A-05）。

涉及：pages/companion/（js / wxml / wxss）

2.2　互动动作优化 第 3 条 · P0

目标：从「图片动一下 + 一句文字」升级为有层次的动作系统。

  • 四个动作：摸摸（蹭一下）、喂食（低头连吃 7 口，1.5 秒）、玩耍（蹦跳）、点击（左右扭）；右上角表情脸随动作变化。
  • 提溜动作：长按 350ms 把宠物拎起来——脚离地 70px、身体摇摆、😾 表情、轻震动；可按住左右拖动，松手压扁回弹并换成 😵。
  • 语音能力预留：utils/voice.js 封装微信同声传译插件，默认关闭、失败静默降级，开启只需三步（后台添加插件 → app.json 声明 → 改开关），不影响当前版本运行。
  • 顺带优化：拖动不跟手、长按跳位、走动中喂食道具错位（见 A-02 / A-03 / A-04）。

涉及：pages/companion/、utils/voice.js（新增）

2.3　社区浏览模式改版 第 5 条 · P0

目标：信息流列表 → 先做「刷抖音」式全屏上下滑，同时保留列表模式可选（清单原意正是两模式并存）。

  • 沉浸式全屏 Feed：竖直上下滑，每条六层结构——模糊铺底、压暗渐变、居中主图、右侧动作栏、底部信息区、顶部悬浮栏。任何照片上的白字都可读。
  • 无图动态不空：用渐变 + 大字排版承接，不会出现半屏空白。
  • 两种模式可切：右下角「列表 / 沉浸」一键切换，选择写入本地存储，下次进入保持上次模式。
  • 预取：剩 3 条时自动加载下一页，滑动不卡顿；沉浸模式无法下拉，顶部提供 ↻ 手动刷新。
  • 布局自适应：Feed 高度由视口决定（fixed 铺满 + 100%），不用任何 JS 像素值，换机型不会留白（见 A-07）。

涉及：pages/community/

2.4　AI 总结「一封信」 第 6 条 · P0

目标：自动汇总近期生活事件与精彩瞬间，以宠物口吻写成一封信，入口放在陪伴页。

  • 生活事件统计层（utils/moments.js，新增）：记录喂食 / 玩耍 / 摸摸 / 被拎起 / 去过哪些场景，按天去重，30 天自动过期，只存本机。
  • 云端写信（cloudfunctions/letter，新增）：聚合近 30 天聊天记录与互动汇总 → 交模型按宠物口吻写成信 → 存库；12 小时最多一封，避免刷信。
  • 无模型也能用：未配密钥时降级为本地模板信（utils/letter-template.js），信里的数字仍全部取自真实统计，页面标注演示模式。
  • 信纸页（pages/letter，新增）：分段排版、称呼与署名识别；信末固定声明「由 AI 根据你们的互动生成，它并不真的记得你说过的话」。
  • 隐私联动：删除宠物时连同信与互动统计一并清除（见 A-09）。

涉及：pages/letter/、utils/moments.js、utils/letter-template.js、cloudfunctions/letter/、api.js / localdb.js（双数据源同步实现）

四、待改功能的需求与要求

以下 5 项尚未实现。每项给出：清单原意 → 要做什么 → 技术方案与取舍 → 需要你决策的点 → 验收标准。建议按 4.1 → 4.2 → 4.3 → 4.4 的顺序推进。

4.1　照片抠图立体效果 第 7 条 · P0 · 建议下一项

清单原意：尝试把用户上传的宠物照片抠图，做成「立体」效果（参考竞品分析）。

现状：照片平铺展示（圆形 / 方形裁切），无主体分离。

要做的事：

  • 上传后自动抠出宠物主体（去背景），保留边缘细节（毛发是难点）。
  • 抠出的主体做立体感，由轻到重三档可选：① 描边光晕 + 落地投影；② 分层视差（背景 / 身体 / 耳头分层，随手机倾斜或走动轻微错位漂移）；③ 轻微 3D 旋转与景深。
  • 与既有能力共存：场景、自主走动、提起拖拽、桌面态页都要能正常渲染抠图后的主体。
  • 抠图失败必须降级：保留原图并给出提示，不能阻断创建流程。

技术方案与取舍：

方案做法优点 / 代价
A（推荐）云函数调第三方抠图 API（如 remove.bg / 阿里云图像分割 / 腾讯云图像处理）落地最快、效果稳定；按张计费，需要一个账号与密钥，抠图结果缓存到云存储，同一张照片只抠一次
B微信云开发自带图像处理能力少一个外部依赖、密钥不落地；需先确认可用接口与计费，能力边界要先验证
C端上分割（小程序端插件 / 端侧模型）无网络往返、无调用费用；模型体积与性能受限，宠物（非人像）主体效果无保证

需要你决策：选哪条路；是否接受按张计费；同一用户反复换照片时是否限制次数。

验收标准：

  • 三种典型背景（纯色墙、室内杂物、室外绿植）照片，主体边缘可用（毛发允许轻微损失）。
  • 抠图成功 → 呈现抠图主体；失败 → 原图 + 提示，创建流程不中断。
  • 同一张照片重复进出不重复调用、不重复计费。
  • 隐私模式下，抠图结果与原始素材在 22 小时有效期后一并删除。

4.2　形象 3D 化升级 第 1 条 · P1

清单原意：宠物只是平面照片 → 改成像「大肥鱼」那种 3D 萌系风格，支持「扑向用户」等动态动作；可设置宠物对主人的称呼（如「叫我妈咪/爹地」）。

要做的事（可拆三步走）：

  • 第一步·称呼自定义：与 3D 无关，可独立先做。设置项落库后，替换所有出现「主人」的文案（气泡、互动反馈、一封信的称呼与署名）。这一项成本最低、感知最强，建议先做。
  • 第二步·伪 3D 分层：抠图主体 + 分层视差 + 透视变换 + 落地投影，随走动、提起、手机倾斜产生立体位移。
  • 第三步·真 3D 形象：每只宠物一套 3D 模型 + 小程序端 3D 渲染（WebGL / Three.js 类库），实现「扑向用户」等骨骼动画。

技术方案与取舍：真 3D 的核心成本不在渲染，而在形象从哪来——逐只建模无法规模化；AI 图生 3D 目前质量和可控性都不稳；通用形象库则失去「这是我的宠物」的意义。因此建议先做第一、二步，真 3D 作为独立项目单独立项评估。

需要你决策：3D 形象来源（AI 生成 / 通用库 / 逐只定制）；是否接受「照片风格化 + 伪 3D」作为长期形态。

验收标准：称呼在全部文案生效且可随时修改；伪 3D 下走动/提起时主体有层次位移且不掉帧；真 3D 若推进，需明确单只宠物的建模与交付流程。

4.3　对话能力升级 第 4 条 · P1

清单原意：模板回复不够智能 → 同时支持文字与语音聊天（真正打语音）；接入 Agent / AI 检测模型提升对话智能度。

现状：cloudfunctions/chat 已有模型适配层（可替换 Provider），未配密钥时走模板回复；语音能力在 utils/voice.js 已封装但默认关闭。

要做的事（三层，可独立上线）：

  • ① 文本智能化：配置模型密钥后，把宠物性格、称呼、近期互动与一封信的素材注入提示词，让回复有连续性（不是每次都从零开始）。
  • ② 语音输入：开启同声传译插件，把语音转文字后走同一套对话链路。改动很小，插件已封装好。
  • ③ 语音输出（「真正打语音」）：需要 TTS 合成。可选微信同声传译的合成能力或第三方 TTS；这是本项成本与体验风险最高的一步，涉及音色选择、首字延迟、长文本切分。

要求：语音开关独立可控（用户可只开输入不开输出）；合成失败降级为文字，不阻塞对话；对话请求需有超时与重试，失败时回落到模板，不能让用户对着转圈等。

需要你决策 / 待确认：按清单备注，技术路线需先咨询老师；音色用通用音色还是定制；TTS 供应商与预算。

验收标准：连续 10 轮对话上下文不丢；语音输入识别可用；语音输出首字延迟可接受且可中断；断网/额度用尽时自动降级且提示清楚。

4.4　性格自定义 第 9 条 · P2

清单原意：目前只有预设标签（忠心 / 活泼 / 贪吃 / 亲人），编辑后无实际表现，仅相当于个人兴趣标注 → 开放用户自定义性格，可详细描述「不同互动场景下宠物的反应」，并根据性格让宠物呈现差异化状态。

要做的事：

  • 性格 → 行为映射表：把抽象性格落成可执行参数。例如「粘人」= 主动靠近频率更高、等待间隔更短；「高冷」= 少主动说话、被摸后延迟回应；「贪吃」= 喂食动作更夸张、看到食物主动跑过来。
  • 场景化自定义描述：让用户填「我下班回家时它会…」这类句子，写进对话提示词与一封信的素材池。
  • 行为可视化差异：走动频率、动作选择偏好、气泡文案池、表情倾向都要随性格变，否则用户感知不到。

依赖：强依赖 4.3 对话能力。若对话仍是模板，性格只能影响动作与文案，说服力不足。

验收标准：同一只宠物切换两种反差性格，连续观察 3 分钟，行为节奏与文案应有明显差异；自定义描述能在一封信与对话中被引用。

4.5　桌宠功能 第 8 条 · P1 · 已结论

结论：微信小程序运行在微信容器内，平台不提供把窗口常驻到设备桌面的能力（无桌面悬浮窗 / 小组件 API），该需求在小程序形态下无法实现，与开发工作量无关。

已交付的轻替代：宠物桌面态页（见 2.6）——用小程序内的仿桌面承接「宠物待在我熟悉的地方」的体验。

可选的进一步补强：订阅消息提醒（宠物「想你」/ 该喂饭了），可在用户授权后定时触达，是最接近「桌宠存在感」的能力。是否要做，等你决定。

六、已知缺口与风险

  • 自动化测试的边界：53 项断言覆盖的是纯逻辑（统计、模板信、导出分区、授权队列、云端源码约束）。有四类必须人工在云环境/真机验证：真实文件删除、定时触发器是否按时执行、云存储权限、隐私授权弹窗流程。已在用例文档中单独标注。
  • 演示模式与云模式存在行为差异：一封信冷却分别是 5 分钟与 12 小时，演示模式放宽是为了方便反复看效果；验收数据不要在两种模式间混用。
  • 尚未做完整真机回归：当前验证以开发者工具 + Node 断言为主，提审前建议按 docs/隐私与数据管理专项测试.md 的用例在真机走一遍。
  • 数据保留的硬约束：照片 22 小时（配合每小时清理，实际 < 24 小时）、聊天 90 天、信保留最近 20 封。任何新增数据类型都必须同步进这张表，否则隐私模式会出现「漏删」。
  • 第 8 条为平台限制：短期无解，不要再投入方案评估。

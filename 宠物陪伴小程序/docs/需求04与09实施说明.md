## 二、参考的外部思路

按「来源 → 核心观点 → 为什么采用 → 落在哪」列出。检索渠道为 GitHub / CSDN / 微信开放文档。

### 1. 人格设定要写成「具体行为」，不能写抽象形容词

- **来源**：CSDN 角色扮演（Role-Play）系统提示词实践类文章，多篇一致。典型表述是「与其写『性格幽默』，不如写『他喜欢用双关语和自嘲来化解尴尬』」。
- **核心观点**：抽象形容词对大模型没有约束力，模型不知道该把它演成什么样；给出可模仿的具体行为模式和语言样本，角色一致性才稳。
- **为什么采用**：`#9` 原需求给的是「忠心 / 活泼 / 贪吃 / 亲人」这类标签，这正是模型无法执行的东西。所以把它降级为「底色」，另外要求用户填写具体场景反应。
- **落在**：
  - `miniprogram/utils/persona.js` 的 `BASE` —— 每个底色配 4 个场景、每场景 2 条具体动作
  - `cloudfunctions/chat/persona.js` 的 `buildSystemPrompt` —— 把场景反应按「这些时候你会这样」结构化输出

### 2. 负面约束比正面期望更有效

- **来源**：同上，角色一致性维护类文章。原文意思是「写『不要说现代词汇』比写『说话要古典』更不容易翻车」。
- **核心观点**：模型对否定指令的把握通常比期望指令更准确。
- **为什么采用**：原来的 prompt 只有正面要求（「简短温暖」「宠物口吻」），模型很容易滑向客服腔。
- **落在**：`cloudfunctions/chat/persona.js` 的「必须遵守」第 6 条——明确禁止「作为一只…」「很高兴为你…」「有什么可以帮您」；`cloudfunctions/letter/index.js` 第 6 条——禁止「时光荏苒」「岁月如梭」。

### 3. 人设必须承载在 system 层，不能只放在 user 消息里

- **来源**：AI 电子手办 / AI NPC 对话系统的技术拆解类文章。
- **核心观点**：角色一致性最基础的保障是把人设写进 `system` 消息；如果 system 说自己是个「助手」，user 里又说「你是宠物」，模型会跟着 system 走，产出编辑腔。
- **为什么采用**：`#4` 改了 chat 的 system prompt；回归检查时发现 `cloudfunctions/letter` 正好犯了这个错——system 写的是「你是一个温柔、克制的中文写作助手」，而 user 里要求写宠物信。这会让「一封信」和聊天区的语气对不上，同一只宠物两副嘴脸。
- **落在**：`cloudfunctions/letter/index.js` 的 `generateWithModel`

### 4. 小程序云函数不支持 SSE，流式只能做「伪流式」

- **来源**：CSDN 微信小程序接入大模型 / AI 对话实战类文章，以及官方云函数返回格式限制。多篇给出同一结论：真流式要走 WebSocket 或云数据库实时监听，成本高；更实用的是云函数一次性返回、前端逐字渲染。
- **核心观点**：用户对等待的感知关键在于「出字之后」——同样 5 秒，转圈 5 秒和逐字输出 5 秒的体感差别很大；但逐字更新要只改当前那条消息节点，不能重渲染整个列表，否则会卡。
- **为什么不采用真流式**：本项目的回复被限制在 50 字以内，为 50 个字引入 WebSocket 或数据库监听，架构代价远大于收益。伪流式在这个量级上体感已经足够。这也符合原代码「单云函数 + 双数据源门面」的整体设计。
- **落在**：`miniprogram/pages/chat/chat.js` 的 `typeIn()` —— 局部路径 `messages[i].content` 逐帧追加，滚动合并进同一次 `setData`

### 5. 上下文按字数/token 裁剪，不能只按条数

- **来源**：CSDN「AI 对话小程序开发实战」类文章。
- **核心观点**：便宜模型的上下文窗口不大，条数够但字数超了一样报错；应该按字数从最近往前累加，超了就停。
- **为什么采用**：原实现是 `limit(10)` 条，如果用户连续发长消息，10 条可能就超窗口。
- **落在**：`cloudfunctions/chat/index.js` 的 `trimContext()` —— 条数上限 10 + 字数上限 1200 双保险

### 6. 语音方案选型：同声传译插件是唯一免服务器路径

- **来源**：CSDN 关于微信同声传译插件的多篇实践文章，覆盖录音识别（`getRecordRecognitionManager`）和语音合成（`textToSpeech`）两套 API。
- **核心观点**：插件把「录音 + 识别」合并成一个流程，比 `wx.getRecorderManager` + 第三方 ASR 简单得多；免费、无需备案、无需服务器。
- **为什么采用**：本项目没有后端服务器，只有云函数。接第三方 ASR 需要额外采购和密钥管理，而插件零成本。这也是原 `utils/voice.js` 已经选定的路径，本次是把 ASR 补齐并做成可降级。
- **落在**：`miniprogram/utils/voice.js` 的 `createRecognizer` / `ensureRecordPermission`

## 四、验收步骤

### #9 性格自定义（5 分钟，演示模式即可）

1. 微信开发者工具打开项目，进入「我的」→ 编辑档案
2. 找到「性格」卡片
   - 选一个底色，下方预览文案要跟着变
   - 点「按你的印象再补充（可选）」展开
3. 选 2 个特质、填口头禅「我要吃鱼」、填「被摸摸时」的反应
   - 预览区应立即变成你写的那句
   - 尝试选第 4 个特质 → 应提示「最多选 3 个」
4. 保存 → 返回「我的」，摘要应显示「亲人 · 黏人、胆小 · 口头禅「我要吃鱼」」
5. 回陪伴页点「摸摸」/「喂食」→ 气泡应显示你填的那句
6. 长按宠物提起 → 气泡应显示你填的「被拎起来时」那句
7. 进聊天页发一句「你好呀」→ 演示回复应带口头禅前缀
8. 点右上「一封信」生成 → 有模型时信的口吻应与聊天一致

### #4 对话升级

**文字部分（10 分钟，无需配置）**

1. 进聊天页，发「今天有点累」
2. 回复应逐字出现，末尾有闪烁光标
3. 往上翻历史时再发一条 → 不应被强行拉回底部，而是出现「有新消息 ∨」提示条
4. 点提示条 → 回到底部
5. 点顶部「自动播报」→ 会提示语音未启用（因为插件没配），这是预期行为

**语音部分（需先配插件，见第五节）**

1. 配好后回到聊天页，点左下角 🎤
2. 点「按住 说话」→ 首次会弹麦克风授权
3. 按住说一句话 → 浮层显示实时识别文字
4. 松手 → 自动发送并收到回复
5. 打开「自动播报」→ 回复会念出来
6. 长按任意宠物气泡 → 重听

## 五、需要你操作的事

### 1. 部署两个云函数

`chat` 和 `pet` 都有改动，必须重新部署，否则性格字段存不进去、prompt 也还是旧的。

- `cloudfunctions/chat` —— 新增了 `persona.js`，是整个目录一起传
- `cloudfunctions/pet` —— 改了 create / update
- `cloudfunctions/letter` —— 回归优化也改了，一起部署

### 2. 启用语音（三选一步骤，缺一不可）

1. 小程序后台 → 设置 → 第三方设置 → 插件管理 → 搜索「微信同声传译」→ 添加
2. 在 `miniprogram/app.json` 的 `window` 同级加：

```json
"plugins": {
  "WechatSI": { "version": "0.3.5", "provider": "wx069ba97219f66d99" }
}
```

3. 把 `miniprogram/utils/voice.js` 第 18 行的 `ENABLED` 改成 `true`

**为什么默认是关闭的**：插件没在后台添加就写进 `app.json`，小程序会**直接编译失败**。所以代码保持可用、开关留给你。这也意味着现在编译能过，但语音按钮点了会提示未启用——这是有意的降级，不是 bug。

### 3. 接真实模型（可选）

在 `chat` 云函数的环境变量里配三项，就会从演示模式切到真实模型，无需改代码：

```
MODEL_PROVIDER = openai-compatible
MODEL_BASE_URL = https://你的服务/v1
MODEL_NAME     = 模型名
MODEL_API_KEY  = 密钥
```

`letter` 云函数同理（独立配置）。

### 4. 隐私指引要补「麦克风」

如果之后要开 `__usePrivacyCheck__`，后台的《用户隐私保护指引》里必须声明**麦克风**用途，否则录音会被拦。这和之前相册那条是同一套机制。

| 需要咨询金亮老师的点 | ①是否要走微信云开发内置 AI（`cloud.extend.AI`，可免密钥调用模型）②是否需要内容安全审核前置。这两点会影响后续架构，但不影响本次交付 |
